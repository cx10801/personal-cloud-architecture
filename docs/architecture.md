# 架构设计

## 1. 分层模型

平台按「变更频率」而非「技术栈」分层。越往下越稳定，越往上迭代越快。

| 层 | 变更频率 | 组件 | 部署位置 |
|---|---|---|---|
| 身份层 | 极低 | 零信任访问控制 + OIDC | 边缘 + 服务器 |
| 网络层 | 低 | DNS、隧道、证书 | 边缘 |
| 数据层 | 低 | 对象存储、键值存储 | 边缘 |
| 应用层 | 中 | 八个无状态 Worker | 边缘 |
| 服务层 | 中 | 常驻进程与容器 | 服务器 |
| 观测层 | 高 | 告警、日志、面板 | 两侧都有 |

这样分层的好处是：应用层随便改，不会碰到身份层的配置；身份层出问题，应用层不受影响（只是全部无法访问）。

## 2. 请求路径

### 2.1 浏览器访问私有应用

```
浏览器
  │ GET https://app.example.com
  ▼
零信任访问控制
  ├─ 无有效会话 → 302 到身份提供方
  │                 └─ OIDC 授权码流程 → 回调 → 签发会话 Cookie
  └─ 有有效会话 → 注入 JWT（含 sub / aud / exp / 自定义声明）
        ▼
   Worker
        ├─ 校验 JWT 签名（JWKS 缓存）
        ├─ 校验 aud 与当前应用匹配
        └─ 放行 → 返回内容
```

**为什么 Worker 还要二次校验？** 因为边缘的访问控制和应用是解耦的：如果只依赖边缘，一旦策略被误配成 `bypass`，应用就完全裸奔。二次校验是一道成本极低的纵深防御。

### 2.2 程序调用 AI 网关

```
SDK（任意 OpenAI 兼容客户端）
  │ POST /v1/chat/completions
  │ Authorization: Bearer <平台签发的 Key>
  ▼
ai Worker
  ├─ 1. 解析 Key 前缀 → 定位租户
  ├─ 2. 查 KV 校验 Key 哈希 + 剩余配额
  ├─ 3. 按请求的 model 查上游注册表
  ├─ 4. 注入真实上游密钥（从 Secret 读）
  ├─ 5. 转发；失败则按顺序切换下一个上游
  ├─ 6. 流式回传，同时累计 token 用量
  └─ 7. 异步写回用量
```

注意第 5 步：失败切换只对**幂等**情形生效（连接失败、5xx、超时）。已经产出部分 token 的流式响应不做重试，否则会出现内容拼接错乱。

### 2.3 公网访问服务器上的服务

```
浏览器 → 零信任访问控制 → 隧道
                            ▼
                      cloudflared（容器内）
                            ▼ 172.17.0.1:PORT
                       宿主机
                            ▼
                       Caddy（本地反代）
                            ▼
                    目标服务（仅监听 127.0.0.1）
```

**这里有个容易踩的坑**：`cloudflared` 跑在容器里时，`127.0.0.1` 指的是容器自身，不是宿主机。要访问宿主机服务必须走 Docker 网桥地址 `172.17.0.1`。而目标服务出于安全只监听 `127.0.0.1`，两者无法直连。

解决方案是加一层桥接：

```
cloudflared → 172.17.0.1:8766 → [socat 桥接] → 127.0.0.1:8765 → 目标服务
```

桥接端口只绑在 Docker 网桥上，安全组不放行，公网不可达。这是「不修改目标服务的监听地址，也不给容器特权」前提下唯一的解。

## 3. 数据模型

### 3.1 三类存储的分工

| 存储 | 适合 | 不适合 | 本项目的用法 |
|---|---|---|---|
| KV | 读多写少、最终一致、按 key 直取 | 复杂查询、强一致、列表分页 | 配置、书签、短链映射、AI Key、邮件索引 |
| R2 | 大对象、需要 S3 兼容 API | 频繁覆盖写 | 网盘文件、图床图片、备份 |
| 服务器本地盘 | 需要 POSIX 语义 | 多实例共享 | 容器数据、日志 |

### 3.2 KV 的键设计

KV 只支持按 key 前缀列举（`list({prefix})`），不支持条件查询。所以键名本身就是索引：

```
bookmark:<category>:<id>        书签，按分类前缀列举
short:<code>                    短链映射，直取
ai:key:<sha256前16位>           Key 索引，直取
ai:usage:<tenant>:<YYYY-MM>     用量，按月分片
mail:<YYYYMMDD>:<id>            邮件，按日分片
```

**按月/按日分片的原因**：单 key 有大小上限，且集中写入同一 key 会触发限流。分片后写入分散，读取时按时间范围列举即可。

## 4. 定时任务

平台有三类定时触发：

| 类型 | 实现 | 用途 |
|---|---|---|
| 边缘 Cron | Worker 的 `scheduled` 事件 | 聚合资讯、清理过期缓存 |
| 服务器 Cron | 系统定时器 | 备份、证书检查 |
| 事件驱动 | 消息队列 → 函数计算 | 告警转发 |

边缘 Cron 的注意点：**没有保证精确触发时间**，且单次执行时长有限制。所以任务必须设计成幂等的、可被打断的。聚合资讯这类任务写成「拉取 → 合并去重 → 覆盖写」，重复执行不会产生脏数据。

## 5. 失败模式分析

按影响面排序：

| 故障 | 影响 | 缓解 |
|---|---|---|
| 服务器宕机 | 身份提供方不可用 → 所有私有应用无法登录 | 无法缓解（单点）。公开的 AI 网关与图床不受影响 |
| 隧道断开 | 服务器侧全部服务不可达 | `cloudflared` 配 `restart: always`，实测重连 < 30 s |
| KV 限流 | 写入失败，读取降级 | 写入端做指数退避；读取端容忍陈旧数据 |
| 上游模型故障 | AI 调用失败 | 注册表内置多上游，按顺序切换 |
| 内存耗尽 | 容器被 OOM Killer 杀掉 | swap 兜底 + 告警；牺牲响应速度换取存活 |
| 证书过期 | 隧道层终结 TLS，不涉及 | 边缘自动管理 |

**结论：这套架构的可用性上限由那一台服务器决定。** 这是有意识的取舍——个人场景下，为 99.9% 到 99.99% 付出的成本远超收益。真正重要的是：**服务器挂了不影响公开服务**，这个隔离做对了。

## 6. 与常见方案的对比

| 方案 | 成本 | 运维负担 | 适合 |
|---|---|---|---|
| 单台 VPS + 面板 | 低 | 中（全部手工） | 需要完全控制、不介意运维 |
| 托管 PaaS | 中 | 低 | 不想碰服务器 |
| 纯 Serverless | 低 | 极低 | 无状态应用为主 |
| **本方案（混合）** | **零** | **中** | **有状态需求少、愿意接受单点** |

本方案的本质是：把能上边缘的都推上边缘，只把真正需要「一台机器」的东西留在服务器上。如果哪天有状态需求消失了，服务器可以直接删掉。
